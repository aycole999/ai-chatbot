# Legal UI Refresh Design

> Date: 2026-04-02
> Scope: 整站 UI 重做，保留现有业务流程、接口契约和核心交互

## 背景

当前项目已从通用聊天模板收敛为“法律文书助手”，但前端界面仍明显保留默认模板痕迹：

- 首页虽然已经是法律咨询页，但视觉层级仍接近普通聊天容器
- 侧边栏、顶部栏、输入区、登录页、表单页之间缺少统一视觉语言
- 空状态无法先建立专业感和信任，再引导普通用户开口提问
- 桌面端和移动端均可用，但都没有形成明确的“法律接待台”体验

本次改造只调整 UI、信息层级和视觉系统，不改业务流程：

- 首页仍然是唯一入口，路径保持 `/`
- 核心聊天流程、步骤流转、上传、语音、表单提交逻辑保持不变
- 登录/注册能力保持不变
- 不新增历史会话、角色分流、营销页或新业务模块

## 目标

1. 把当前首页聊天页升级为“现代法律接待台”，让用户一进入就感到专业、可信、易于开始咨询
2. 统一首页、聊天过程、侧边栏、顶部栏、登录/注册页、内嵌表单的视觉系统
3. 让普通用户觉得容易开口，同时让律师用户也接受整体专业度
4. 同时照顾桌面端和移动端，不让任一端退化成另一端的缩略版

## 非目标

- 不改变 `useLegalChat` 的业务状态机
- 不重做法律问答、文书生成、附件分析、语音识别的流程定义
- 不新增第二入口、分流页、落地页或长营销页
- 不在本次改造中引入会话历史功能

## 决策记录

| 决策项 | 选择 | 原因 |
|--------|------|------|
| 首页结构 | 主页即聊天页 | 用户要求保留单入口 |
| 整体气质 | 专业稳重 | 需要法律服务场景的可信感 |
| 视觉材质 | 现代系统感 | 比“纸质文书感”更冷静、更像成熟数字产品 |
| 首页空状态 | 专业引导优先 | 先建立信任，再引导提问 |
| 主方案 | 单画布接待台 | 最适合单入口首页和现有聊天流程 |
| 文案语气 | 通俗易懂 | 同时照顾普通用户与律师用户 |
| 改造范围 | 整站重做 | 用户明确要求重做，而非轻量润色 |

## 视觉 Thesis

把产品做成一个“现代法律接待台”，而不是一个默认聊天模板，也不是一个重营销的官网。

核心视觉特征：

- 深海军蓝 + 冷灰白作为主色基底
- 低饱和、低噪声、薄边框、轻阴影的系统表面
- 明确但克制的层级，不依赖大面积卡片堆叠
- 通俗、可信、接待式的文案，而不是冷硬法条语气

## Content Plan

首页首屏只承担四个职责：

1. 让用户知道这是做什么的
2. 让用户感觉这里是专业可信的
3. 给出少量可立即理解的提问方向
4. 让用户无犹豫地开始输入

内容顺序固定为：

1. 品牌/标题
2. 一句价值说明
3. 3 个左右示例问题或能力标签
4. 输入区

开始咨询后，首屏引导内容自动降级，消息流成为主舞台。

## Interaction Thesis

动效只服务于层级切换与输入反馈，不服务于装饰。

本次改造保留三类关键动效：

- 页面进入时的轻量渐入和位移
- 空状态引导区在首次发言后的收缩/折叠
- 输入框、按钮、抽屉、消息出现时的短时反馈

动效原则：

- 桌面和移动端都要平稳
- 时长短，存在感低
- 不出现夸张弹跳、炫光、浮夸渐变

## 1. 首页聊天页设计

### 1.1 总体结构

首页仍使用 `app/(legal)/(site)/page.tsx` 作为唯一入口，结构保持：

- 顶部系统栏
- 左侧辅助栏（桌面端）
- 主咨询画布

但视觉重心会从“普通聊天列表”切换为“先接待，再进入咨询”的单画布结构。

### 1.2 空状态

当 `messages.length === 0 && !isLoading` 时，主区展示接待式空状态：

- 一个短标题，明确产品用途
- 一句说明，强调适用场景与专业协助
- 3 个左右示例问题/能力标签
- 一条系统欢迎消息
- 突出的输入操作面板

空状态不能演变成长首页，不增加多段营销内容，不做冗长介绍。

### 1.3 首次发言后的状态切换

用户发出第一条消息后：

- 顶部引导区收缩为一条上下文提示带或小型说明区
- 消息流上移成为主要阅读区域
- 输入区保留在底部，作为统一操作面板

此变化只影响视觉层级，不影响 `useLegalChat` 状态与消息数据结构。

### 1.4 消息区

消息区继续承载：

- 欢迎消息
- 用户/助手对话
- 阶段交互组件
- 加载态
- 错误态
- 文书生成操作入口

但视觉会做以下统一：

- 用户消息与助手消息采用同一圆角体系
- 助手消息更偏轻表面，用户消息更偏深色强调
- 长文本、附件、分析结果与阶段表单遵循统一间距与容器规则

### 1.5 输入区

当前输入区由 `Textarea`、附件预览、录音模式、发送控制零散组合而成；改造后会变成“统一操作面板”：

- 面板本身承担输入、附件、语音、发送的总容器
- 面板边界、内边距、控件尺寸统一
- 禁用、聚焦、上传中、录音中等状态使用同一套视觉反馈

录音模式和普通输入模式仍保留现有业务切换，但样式需属于同一套组件表面。

### 1.6 移动端

移动端依然是首页聊天页，不新增单独首页。

移动端首屏优先展示：

- 顶部品牌条
- 精简引导区
- 第一条系统消息
- 输入面板

侧边栏收进抽屉，不在首屏并列展示。

## 2. 侧边栏与顶部栏设计

### 2.1 侧边栏定位

当前侧边栏由于没有历史会话，容易显得空。改造后，侧边栏的定位改为“低存在感辅助栏”：

- 品牌区
- 新建咨询动作
- 当前系统状态说明

不强行补充无意义模块，也不把空白区域伪装成复杂导航。

### 2.2 桌面端侧边栏

桌面端采用窄侧栏：

- 深色背景，强调与主画布的主次关系
- 内容密度低，避免喧宾夺主
- 品牌、新建咨询按钮、状态说明形成稳定垂直节奏

### 2.3 顶部栏

顶部栏改为更精炼的系统条：

- 左侧承载侧边栏开关与品牌识别
- 右侧仅保留必要的全局动作
- 不做厚重标题栏，不重复首页主标题

### 2.4 移动端导航

移动端顶部栏只保留：

- 菜单入口
- 品牌名
- 必要操作按钮

侧边栏通过抽屉打开，避免打断首页单入口体验。

## 3. 登录/注册页与表单系统设计

### 3.1 登录/注册页

认证页不再只是默认居中的表单盒子，而是同一视觉系统下的轻品牌页面：

- 共享站点配色、背景和品牌语气
- 表单仍是主角，但外部空间不再空洞
- 文案更像“开始咨询前请先登录”的接待逻辑，而不是纯技术登录提示

### 3.2 表单系统

以下表单统一纳入同一套视觉规则：

- 登录/注册表单
- `FillQuestionsForm`
- `SupplementForm`
- 其他内联输入、下拉、日期输入

统一内容包括：

- 标签字重与颜色
- 输入框高度、圆角、边框与焦点态
- 主按钮、次按钮、禁用态
- 必填项标识
- 错误提示与辅助文本

### 3.3 表单布局原则

- 优先单列结构，减少视觉噪声
- 字段间距统一
- 重要按钮固定在清晰位置
- 在移动端保证触控舒适度和首屏可理解性

## 4. 全局视觉系统

### 4.1 设计 Tokens

优先通过 `app/globals.css` 重建整站 tokens：

- 颜色
- 圆角
- 边框
- 阴影
- 焦点环
- 前景/次前景/弱文本
- 侧边栏专用色

目标是让 `button`、`input`、`textarea`、消息容器、表单块、导航容器都由同一套 token 驱动。

### 4.2 Typography

整站字体需更像专业产品系统：

- 标题清晰但不过度营销化
- 正文适合长段阅读
- 表单与按钮文本具备稳定可读性

实现时可在现有字体变量基础上，补一套更适合中文界面的无衬线方案；若加载成本不合理，则保持当前变量体系，但重新校准字号、字重和行高。

### 4.3 控件风格

控件统一采用：

- 中等圆角
- 低噪声边界
- 明确焦点态
- 稳定的 hover/active/disabled 状态

避免出现：

- 默认模板式厚卡片
- 大面积高饱和渐变
- 过重阴影
- 不统一的圆角和控件高度

## 5. 业务与数据流约束

本次为 UI 改造，现有业务流必须保持：

1. 页面加载后初始化会话
2. 空状态展示欢迎内容
3. 用户输入后进入正常咨询流
4. 阶段组件继续在消息流内渲染
5. 需要生成文书时仍使用原有消息操作入口
6. 错误、加载、流式响应、录音模式继续按原有逻辑工作

换言之：

- `hooks/use-legal-chat.ts` 是状态与业务源头
- `components/legal/legal-chat.tsx` 主要承担结构重排与视觉状态切换
- `components/legal/step-renderers.tsx` 保留交互含义，统一视觉样式

## 6. 错误处理与状态设计

以下状态必须在新界面中有明确表达：

- 加载中
- 流式输出中
- 表单提交中
- 文件上传中
- 语音录制中
- 错误消息
- 会话结束
- 无历史记录说明

状态设计原则：

- 不靠纯颜色表达状态
- 错误态与禁用态要显著，但不能破坏整页秩序
- Loading 与 Streaming 的视觉形式要和整体系统一致，不再像临时占位

## 8. 测试与验收

### 8.1 功能回归

需要确认以下能力未被 UI 改造破坏：

- 首页加载与会话初始化
- 文本发送
- 文件上传
- 语音输入
- 阶段表单提交
- 文书生成入口
- 新建咨询
- 登录/注册

### 8.2 视觉验收

需要至少覆盖以下视口：

- 桌面宽屏
- 常规笔记本
- 手机竖屏

验收标准：

- 首页第一屏不再像默认聊天模板
- 空状态具备专业引导但不过长
- 首次发言后层级切换自然
- 侧边栏不再显得空且抢戏
- 登录/注册页与首页属于同一产品体系
- 聊天内表单与认证页表单具有一致语言

### 8.3 工程验证

至少执行：

- `pnpm lint`
- 手动检查桌面与移动端布局
- 手动走通首页咨询、登录、注册和表单填写流程

如现有 Playwright 用例覆盖到相关路径，应额外跑相关 smoke 流程验证无回归。

## 9. 风险与注意事项

- 视觉重做容易顺手改动结构，需避免触碰业务流程
- 首页引导内容若过多，会削弱“单入口直接咨询”的效率
- 当前无历史记录，侧边栏要接受“简而不空”，不能为填满而添加噪声
- 样式 token 变更会影响整站基础组件，需要注意表单与消息组件的一致性

## 10. 实施结论

本次 UI 改造采用“单入口首页 + 单画布接待台 + 现代系统感材质”的方案。

实现完成后，产品应呈现为：

- 对普通用户足够友好，愿意开始提问
- 对律师用户足够专业，不像消费级聊天玩具
- 对整站而言具备统一、稳定、可持续扩展的视觉系统
